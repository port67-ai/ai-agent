## CHG-0004 — bounded MVP runtime
`/portal` is a separate Next.js client workspace calling `/api/factory/[...path]`. `src/lib/factory/model.ts` owns contracts; `engine.ts` owns immutable strategy/asset content and authorised state transitions; `service.ts` owns authentication, project scope and orchestration; `repository.ts` serialises atomic local writes or a configured dedicated Firebase workspace transaction. `registry.ts` defines reviewed versioned research/human/template capability contracts. Components are split by research, direction, production assets, intake and capabilities.

Only the service reads private records. Customer projection strips internal drafts/tasks/audit/registry proposals and pauses delivery during an unshared revision. Research reservations carry expiring leases, frozen brief/hash, provider metadata and usage status; operator recovery never silently retries a possibly billed call. Source -> interpreted insight -> strategy hash -> specialist task -> asset hash -> approval/delivery is the traceability chain. No queue, permanent agent loops or external publishing is introduced. Local mode is single-process/durable-disk only; Firebase mode and external research remain unverified integrations.

Live-foundation modules: config.ts supplies secret-free readiness and production gates; synthesis.ts validates bounded reviewed-context model responses; synthesis-run.ts reserves/meter/validates/applies drafts. Research and synthesis share invocation limits. See RENDER_ACTIVATION.md and ADR-0002.

CHG-0009: verified Firebase identity -> server-derived account scope -> account/project repository. All managed model dispatches pass metering.ts before fixed-endpoint providers.ts; costs live in separate admin namespaces. New account Firestore documents use v2 layout; legacy snapshots unchanged. See ACCOUNTS_PROVIDERS_COSTS.md and ADR-0003.


## CHG-0062 — native research intelligence
Research roles now include adjacent, trends and video in the existing single-active-run project execution path. research-catalog.ts provides scoped discovery/source routing and legacy coverage; public-video.ts validates YouTube references; video-intelligence.ts validates native Gemini observations. service.ts authorises/reserves/meter/completes direct video through the research path and pins full public context. External page/video data remains untrusted, and outputs remain unreviewed. No separate Python service, queue or social firehose was introduced. See RESEARCH_INTELLIGENCE.md.


## CHG-0082 — customer task coordinator (16 November 2026)

New HTTP project intake creates a task plan through `task-plan.ts`; legacy records have no plan until explicit producer adoption. The existing Next.js service and local/Firestore repositories remain the execution boundary. `planProject` builds a validated versioned dependency graph from public customer requirements, requested formats and launch channels. It records selected and excluded research agents with reasons. An operator may revise selection with an expected-version check and reason before direction work; unknown capabilities and missing foundational research are rejected.

`syncTaskPlan` reconstructs task states from authoritative project runs, evidence, review, direction and asset records and is called within repository mutations. `producer-agent.ts` consults planned dependencies for scope/research and retains the bounded audited reviewer/drafting commands. New paid research is rejected before scoping if excluded; reservations recheck selection and freshness atomically. Synthesis/content and production enforce plan dependencies in addition to their existing gates. Task input identity is stored on runs; late stale output retains usage but cannot become evidence. This is durable state and restart reconstruction, not durable queue delivery; task dispatch remains request/background-driven and existing per-project in-process orchestration locking remains.

`TaskPlan.tsx` shows assignments, reasons, dependencies, producer actions, progress and history in Overview; initial brief forms collect work and optional output requests. `RunTracker` consumes the same plan. The global system map remains the capability/API catalogue and now shows task manager feeding the orchestrator; it is not an editable project DAG. Research preparation/progress uses selected roles. Existing projects and the synthetic demo keep their old path until explicitly adopted. External agent harness types remain an extension point, not an implemented external-bot connector.


## CHG-0083 — AI research and medium planning

`research-planner.ts` builds the complete authorised public brief/channel/method context and validates a strict seven-role proposal. `planning-run.ts` provides transactional reservations, bounded invocation counts, metering, freshness checks, history and capability-proposal routing. The task manager applies only approved role IDs and constructs the dependency graph itself. Accepted role questions/methods are pinned to research task scope; compatible completed research survives revisions while affected sources/insights are invalidated. `scope-run.ts` derives a cached scope from the accepted plan and preserves explicit producer scope edits. No paid scope call can bypass pending/failed planning.

`medium-selection.ts` runs after accepted sources/insights and proposes format-channel pairs. A cited recommendation must name linked accepted sources and insights; a channel prior has limited confidence. There is no connected measured performance dataset. `mediumDecision` records rationale and expected recommendation/evidence context; the request, recommendation and production choice are distinct records. Producer confirmation rejects unseen changed evidence or versions. A confirmed video alternative adds a bounded video research prerequisite, retaining compatible existing evidence. Additional evidence invalidates the old recommendation and requires fresh confirmation.

The two planning slots inherit explicit stage defaults or existing scoping/format model routes before environment settings, with visible source attribution; no provider-call fallback/retry is hidden. New public explicit work-type intake opts into planning; legacy clients remain compatible and producers can enable it explicitly. Planning failures block dependent execution until deliberate retry or rules selection. Catalogue gaps enter the existing proposal backlog, never the executable capability registry. `research-methods.ts` contains original Port67 method guidance, applied through the existing grounded adapters. No generic framework, new vendor or distributed queue is added.

## Selective specialists and feedback (CHG-0084)
The fixed research catalogue now includes channel, offer and measurement roles, each on the existing public grounded adapters and metering. Legacy seven-role projects retain their selected researchers. performance.ts validates immutable observations, parses bounded CSV and calculates deterministic ratios. Producer reviews plus separate PUBLIC authorisation control model context. Project-local history enters planner and medium payload hashes; explicit same-account carry copies accepted authorised reports into later projects as pending observations. No training job or private advertising API is implied.


## CHG-0104: video workspace and customer accounts
`/workspace` (src/app/workspace, Workspace.tsx) is a separate client shell for producers and admins, with Overview and Projects placeholders and the Customer account page (CustomerAccounts.tsx, CustomerEditor.tsx, workspace-api.ts). `customers-api.ts` handles every `customers...` route and is called from `handleFactory` right after the sign-in check, before the existing routes; it refuses customers and the demo. Pure rules and the website link reader are in `customers.ts` (client-safe); state changes with audit are in `customers-commands.ts`; brand purpose files are in `customer-store.ts` (private Firebase Storage or local folder, never a public URL); `site-links.ts` is the only code that fetches an arbitrary public address: it resolves DNS itself, refuses non-public addresses, pins the connection to the checked address, keeps redirects on the same site and caps size and time. Records are stored through the existing repository in the system workspace `factory-customers`. The old portal, studio code and the customer role are unchanged. See ADR-0004 and docs/superpowers/specs/2026-11-25-video-workspace-design.md.
